LSDB is lazy: nothing below actually runs until you ask it to. The snippets tagged ⚡ triggers computation are the ones that do.

load a catalog#

finding

data.lsdb.io is the catalog browser: Gaia, ZTF, SDSS, 2MASS, DES, and more, each with its row count, size on disk, and a copy-paste URL. Catalogs are mirrored in several regions — grab the one nearest you, and prefer an s3:// endpoint over https:// when you have one.

Browse data.lsdb.io Reading the catalog browser Other data centers

opening

open_catalog reads the catalog's metadata and nothing else. You get back a Catalog that knows its columns, types, and partitioning, but holds no rows.

python 
import lsdb

ztf = lsdb.open_catalog(
    "https://data.lsdb.io/hats/ztf_dr14/ztf_object",
    columns=["ra", "dec", "ps1_objid", "mean_mag_r"],
)
ztf
Some catalogs come as collections

A collection bundles a catalog together with its margin and index catalogs, so opening one brings the margin along at .margin. It matters when you crossmatch — which is where margins earn their keep, and where the details live.

picking columns

Every catalog defines a set of default columns, loaded when you don't ask for specific ones. That default exists to stop you accidentally pulling two hundred columns across the network. Name what you need and the rest is never read.

python used in column_filtering.ipynb 
# What am I getting by default, and what else is there?
ztf.columns
ztf.all_columns
This is the cheapest speed-up available

Column selection is pushed down into the parquet reader, so unselected columns cost you nothing — not bandwidth, not memory. It is usually a bigger win than anything you will do with a Dask cluster.

go faster#

cut it down first

Write your whole workflow against one small region of sky. Check the results look the way you expected. Then delete the search and run the same code on the full catalog. This is the habit that saves the most time while you are still figuring out what you want, because a mistake costs you seconds instead of an hour.

A region search narrows partitions and rows, so you read a handful of files rather than thousands.

python 
# While developing: one degree of sky.
gaia = gaia.cone_search(ra=180.0, dec=10.0, radius_arcsec=3600)

# When it all works, delete that line and the same code runs on the full catalog.

There are other shapes when a cone doesn't fit: box_search, polygon_search, moc_search, and order_search.

ask for fewer columns

Covered up in picking columns, but it belongs here too. It is the cheapest speed-up to apply — one keyword argument, no restructuring — and unselected columns are never read at all.

start a Dask client

LSDB runs on Dask. Without a client you still get parallelism across your cores; with one you get a dashboard showing exactly what is running, how much memory each worker holds, and which task is the bottleneck.

python used in dask_client.ipynb 
from dask.distributed import Client

client = Client(n_workers=4, threads_per_worker=1, memory_limit="auto")
client  # displays a link to the dashboard

In a script, a context manager guarantees the cluster shuts down even if the work fails. In a notebook you usually want the opposite — one client kept alive across many cells, closed with client.close() when you are done.

⚡ triggers computation python used in dask_client.ipynb 
with Client(n_workers=4, threads_per_worker=1) as client:
    result = matched.compute()
Configuring a Dask client Dask cluster tips Decoding alarming Dask messages
More workers is not always faster

Each worker needs enough memory to hold the partitions it is handling. Four workers with room to breathe will beat sixteen that spend their time spilling to disk. If the dashboard is mostly orange, you have too many workers, not too few.

read the nearest copy

Catalogs are mirrored across regions and providers. s3:// endpoints generally outperform https://, and if you are working on a cluster that already holds a local copy, use that instead of pulling across the internet at all.

examine the catalog#

look at a few rows

head() is the cheap way to see real values: it reads from the first partitions that have data rather than computing everything.

⚡ triggers computation python used in catalog_object.ipynb 
gaia.head()          # a handful of rows
gaia.head(20)
⚠ Do not call .compute() to have a look

compute() pulls the entire result into your machine's memory. On a survey catalog that is not a slow operation, it is an impossible one — it will exhaust your RAM and take the kernel with it. Use head() to look, and save compute() for results you have already cut down.

find out how big it is

Before you compute anything, ask what it would cost. estimate_size() prints a report based on metadata alone — no row data is read.

python 
gaia.npartitions     # how many files this workflow will touch
gaia.estimate_size()
You selected 3/152 columns. You selected 2016/2016 pixels. Expect up to 1,812,731,847 results (100.00% of the full catalog). Expect up to 42.1 GiB in MEMORY. Expect up to 37.2 GiB on DISK.

That is the number worth checking before you reach for compute().

check column statistics

HATS stores per-column minimum, maximum, and null counts in the parquet footers, so LSDB can report them across the whole catalog without touching a single row of data. This returns immediately even on a billion-row catalog.

python 
gaia.aggregate_column_statistics()      # min, max, null_count, row_count
gaia.per_partition_statistics()         # the same, broken down by partition

These come from the catalog's own recorded metadata, so on a catalog you have already filtered they describe what was there originally — LSDB warns you when that happens.

modify the catalog#

select a region of sky

Region searches are how you cut a catalog down spatially. Each runs in two stages: a coarse filter that decides which partitions to open at all, then a fine filter on the rows inside them. Pass fine=False to keep whole partitions and skip the second stage.

python used in region_selection.ipynb 
gaia.cone_search(ra=180.0, dec=10.0, radius_arcsec=3600)
gaia.box_search(ra=(179.0, 181.0), dec=(9.0, 11.0))
gaia.polygon_search([(179.0, 9.0), (181.0, 9.0), (181.0, 11.0), (179.0, 11.0)])

There are more: moc_search for an arbitrary sky region as a MOC, order_search to select by partition order, and id_search to look up known objects by identifier using an index catalog. You can also write your own.

filter rows

query() takes a pandas-style expression string and stays lazy. Column names that aren't valid Python identifiers go in backticks; @variable is not supported, so interpolate with an f-string instead.

python used in row_filtering.ipynb 
bright = gaia.query("phot_g_mean_mag < 19")

limit = 18.5
brighter = gaia.query(f"phot_g_mean_mag < {limit}")

apply your own function

map_partitions hands your function one partition at a time as a pandas dataframe, in parallel, across the whole catalog. Dask works out the resulting columns by running your function on an empty frame; pass meta explicitly when that guess comes out wrong, or when running your function even once is expensive.

python used in map_partitions.ipynb 
def add_flux(df):
    df["flux"] = 10 ** (-0.4 * df["phot_g_mean_mag"])
    return df

with_flux = gaia.map_partitions(add_flux)

When your function is naturally per-object rather than per-partition, map_rows is the friendlier option — it handles the packing and unpacking for you, including nested columns.

Everything returns a new catalog

Filters and maps never modify in place; each returns a new lazy Catalog built on the previous one. Chain them freely — nothing is read until you compute.

work with nested data#

Light curves, spectra, and detection histories are many measurements per object. A nested column holds a whole sub-table inside each row, so one row stays one object no matter how many epochs it has. See Ask for what that means for the data model.

nest list columns

Plenty of catalogs ship light curves as parallel list columns — ZTF DR22 gives you hmjd, mag and magerr as arrays. nest_lists folds those into one nested column you can work with as a unit.

python used in nestedframe.ipynb 
lc = lsdb.open_catalog(
    "https://data.lsdb.io/hats/ztf_dr22/ztf_lc",
    columns=["objectid", "objra", "objdec", "nepochs", "hmjd", "mag", "magerr"],
)

lc = lc.nest_lists(
    base_columns=["objectid", "objra", "objdec", "nepochs"],
    list_columns=["hmjd", "mag", "magerr"],
    name="lc",
)
lc.nested_columns          # ['lc']

get one value per object

This is the common shape: reduce each object's light curve to a number, and keep it beside the object. map_rows passes each row in, nested column included.

python used in timeseries.ipynb 
import numpy as np

mean_mags = lc.map_rows(
    lambda row: float(np.nanmean(row["lc"]["mag"])),
    columns=["lc"],
    meta={"mean_mag": "float64"},
    output_names="mean_mag",
    append_columns=True,      # keep the original columns alongside the result
)

Two related shapes worth knowing: join_nested attaches another catalog's rows as a nested column, and crossmatch_nested does the same for crossmatch results — so a many-to-one match stays one row per object.

crossmatch#

match two catalogs

Crossmatching is positional and lazy. LSDB aligns the two catalogs' partitions, then matches within each overlapping pair — so nothing is loaded until you compute.

⚡ triggers computation python used in crossmatching.ipynb 
matched = ztf.crossmatch(
    gaia,
    radius_arcsec=1.0,
    n_neighbors=1,
)
matched.head()
crossmatch reference

not get wrong answers

⚠ Crossmatch without a margin and you get wrong answers, silently

Objects near a partition boundary have their true nearest neighbour in the next partition. Without a margin catalog on the right-hand side, those matches are simply missed, and your result is incomplete along every partition edge.

LSDB warns you — “Right catalog does not have a margin cache. Results may be incomplete and/or inaccurate.” — but it is a RuntimeWarning, not an error. In a notebook, buried in Dask progress bars, it is very easy to miss, and the numbers you get back look perfectly reasonable.

require_right_margin defaults to False, so nothing stops you. Either open the right catalog as a collection, or pass its margin_cache explicitly — then turn the check on so it fails loudly if the margin ever goes missing.

python used in margins.ipynb 
gaia = lsdb.open_catalog(
    "https://data.lsdb.io/hats/gaia_dr3/gaia",
    margin_cache="https://data.lsdb.io/hats/gaia_dr3/gaia_10arcs",
    columns=["ra", "dec", "source_id", "phot_g_mean_mag"],
)

matched = ztf.crossmatch(
    gaia,
    radius_arcsec=1.0,
    require_right_margin=True,   # raise instead of quietly under-matching
)
Margins, in depth

keep unmatched rows

how="inner" (the default) keeps only objects that matched. how="left" keeps every row of the left catalog, filling in nulls where nothing matched — useful when the question is "which of my objects have no counterpart?"

python used in types_of_crossmatch.ipynb 
everything = ztf.crossmatch(gaia, radius_arcsec=1.0, how="left")

# Name the columns yourself when both catalogs share column names.
labelled = ztf.crossmatch(gaia, radius_arcsec=1.0, suffixes=("_ztf", "_gaia"))
There is no right or outer join

how accepts "inner" and "left" only. For the mirror of a left join, swap which catalog you call .crossmatch() on.

use my own algorithm

The default is a k-d tree nearest-neighbour match. To match on something other than sky position — colour, proper motion, a probabilistic score — subclass AbstractCrossmatchAlgorithm and hand it over.

python 
from lsdb import AbstractCrossmatchAlgorithm

class MyMatch(AbstractCrossmatchAlgorithm):
    def perform_crossmatch(self):
        ...  # return matched indices and any extra columns

matched = ztf.crossmatch(gaia, algorithm=MyMatch)

save my results#

pull it into pandas

Once the result is genuinely small, compute() gives you an ordinary in-memory dataframe to plot, fit, or hand to another library.

⚡ triggers computation python used in exporting_results.ipynb 
result = bright.cone_search(ra=180.0, dec=10.0, radius_arcsec=600).compute()
result.to_csv("my_result.csv")

write a HATS catalog

When the result is too big for memory, or you want to pick up where you left off tomorrow, write it back out as a HATS catalog. It reopens with open_catalog like any other, and it is partitioned, so the next workflow starts fast.

⚡ triggers computation python used in exporting_results.ipynb 
bright.write_catalog(
    "./my_catalogs/bright_gaia",
    catalog_name="bright_gaia",
    overwrite=True,
)

again = lsdb.open_catalog("./my_catalogs/bright_gaia")
This is the checkpoint you want before lunch

A crossmatch that took twenty minutes should not have to run twice. Writing the result costs one line, and reopening it is instant.
